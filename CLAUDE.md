# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A **JetBrains plugins project** (see `README.md`). The active plugin is **Keymap Manager** (ID `de.civa.plugins.keymapmanager`, display name "Keymap Manager"). It is a **macOS-focused keymap manager**: find and resolve shortcut conflicts, rebind/remove shortcuts in place, import/export keymaps as XML, and manage installed keymaps (select/activate/duplicate/rename/delete); it also bundles the **MacBook Pro DE** keymap as a ready-made starting point for JetBrains IDEs on macOS. The driving constraint for that keymap is a **German (T1/ISO) keyboard on a MacBook Pro** — many stock IntelliJ bindings are physically unpressable there and are being replaced.

`keymaps/keys.md` is the canonical reference: the German-layout constraint, the audit of every key the keymap uses, and the machine-verified table of bindable German keys (umlaut hex encoding). Read it before touching keymap XML. (A more detailed research doc, `handover-unreachable-keys.md`, exists locally but is gitignored — do not rely on it being present.)

## Commands

```bash
# Build the plugin ZIP  →  keymap-plugin/build/distributions/Keymap-Manager-<version>.zip
# (<version> comes from build.gradle.kts; currently 1.6.1)
cd keymap-plugin && ./gradlew buildPlugin

# Launch a sandbox IDE with the plugin loaded (for manual verification)
cd keymap-plugin && ./gradlew runIde

# Verify API compatibility against the target IDE (internal/experimental/deprecated-API usage)
# → verdict under build/reports/pluginVerifier/<IDE>/…/verification-verdict.txt
cd keymap-plugin && ./gradlew verifyPlugin
```

There are no tests or linters. After editing keymap XML, verify with an ad-hoc Python script (xml.etree): well-formed, action ids unique and alphabetically sorted, every id present in `keymaps/$default.xml` or `keymaps/Mac OS X 10.5+.xml` (unknown ids fail **silently** at runtime), and only `keyboard-shortcut` / `mouse-shortcut` / `keyboard-gesture-shortcut` child elements (anything else throws `InvalidDataException` at load). Exception to the id check: three intentional empty `<action/>` overrides — `Terminal.ClearPrompt`, `Terminal.SearchInCommandHistory`, `Vcs.CombinedDiff.ToggleCollapseBlock` — are **not** in the reference keymaps; they clear conflicting plugin default shortcuts (Terminal/VCS ship in all JetBrains IDEs), so don't treat them as unknown-id errors.

Install/activation steps for the built ZIP: `keymap-plugin/INSTALL.md`.

## Structure and data flow

- `keymaps/MacBook Pro DE.xml` — **working copy / source of truth** for the keymap. It is a *flattened* merge of `$default.xml` and `Mac OS X 10.5+.xml` (Mac entries win; stale conflicting shortcuts pruned): all ~447 bindings are re-stated explicitly even though `parent="Mac OS X 10.5+"` would inherit most, deliberately pinning them against upstream changes.
- `keymap-plugin/src/main/resources/keymaps/MacBook Pro DE.xml` — the plugin resource, a **manual copy** of the file above. After editing the working copy, `cp` it here and rebuild; nothing syncs them automatically.
- `keymaps/$default.xml`, `keymaps/Mac OS X 10.5+.xml` — reference copies of the platform keymaps. All three keymap files are sorted alphabetically by action id for side-by-side diffing; keep them sorted.
- `keymaps/orig/` — pristine platform exports; do not modify.
- `keymaps/keys.md` — generated audit of every modifier/key used, with German-layout reachability. Appendix A (37 actions with no reachable binding) is the rebinding work list.
- `keymap-plugin/` — Gradle project: `plugin.xml` + the keymap XML, wired via the `bundledKeymap` extension point, plus six Java classes: `NationalLayoutCheck` fires a startup/keymap-change notification for **whatever keymap is active** — a warning with a one-click fix when *our* keymap is active while JBR national keyboard layout support (`com.sun.awt.use.national.layouts`, default on for macOS) is off (without which the German-key bindings never fire), otherwise a plain nudge to review conflicts; the warning and the nudge latch **independently** (one-shot each), so switching to our keymap still warns even if the nudge already fired; both carry the "Open Keymap Manager" action. `ConflictScan` + `ConflictAdvice` + `ConflictReportDialog` implement the live report, also opened by `ShowConflictReportAction` (Tools → Keymap Manager). The dialog has three parts — a keymap **selector** row, `centered` **on the window**: the dropdown of all installed keymaps (active first, then this plugin's, then the rest, each tagged with its source; Activate/Reset for a non-active pick sit centered under it), then the **action filter** field beside it (spec 0004 — see below), with the help "?" pinned right (it opens `HelpDialog`: the usage walkthrough, closed by an **About** block — `aboutHtml()` — whose plugin name/version/vendor come from the plugin's own `IdeaPluginDescriptor` (looked up by `PLUGIN_ID`, so they can't drift from `plugin.xml` / `build.gradle.kts`), plus the source link and the environment a bug report needs: IDE + build number (`ApplicationInfo`), JVM and OS from plain system properties (**not** `SystemInfo`, whose constants the platform marks obsolete), and the plugin's two runtime dependencies — `scan.jbrApiAvailable` and `NationalKeyboardSupport.getEnabled()`. `htmlPane` now carries a `HyperlinkListener` → `BrowserUtil.browse`, so those `<a href>`s actually open). Two layout details are load-bearing there: the help button sits in a **`GridBagLayout`** holder so it is **vertically centred** on the row (a `FlowLayout` lays its child out at the *top* of the combo-height EAST slot, which left the "?" floating above the row), and a `mirrorSpacer(helpHolder)` — an empty strut as wide as that holder — goes in **WEST**, because `BorderLayout` hands EAST its width first and CENTER alone would sit half the help button's width left of true centre (and off the buttonRow's centre below). Also a **gear menu** — a flat `InplaceButton` whose icon is a `LayeredIcon` of `GearPlain` with `ButtonDropTriangle` overlaid at the bottom-right corner, opening a real IDEA action menu (`ActionManager.createActionPopupMenu`) — holding **Export…**, **Import…** and **Duplicate** (derive an editable copy and preview it) always, **Rename**/**Delete** for an editable keymap (Rename inline in the combo's slot via a CardLayout swap — Esc cancels, Enter saves, re-registered under the new name (duplicate names, and reserved ones — the `Mac OS X` prefix or an official keymap name — are refused); Delete with confirmation, falling back to the parent keymap), and, in a separate bottom section, a **Show modified only** toggle (hides the conflict sections, leaving just the Modified-shortcuts view) and a **Show Action IDs** toggle and a **Show Keymap** toggle (both default off — Show Action IDs appends each action's id, Show Keymap appends the keymap that *defines* the current binding (nearest declaring ancestor up the parent chain, `definingKeymapName`); shown **dimmed** next to the action name in **every** surface — navigator (incl. conflict/double-bound/overlap rows, via the first action), detail pane, the conflict action list (`ActionListView`), the section-contents listing, and the confirm-dialog lists. In every **list** surface it sits in the **right-hand column, just before the keycaps** — the row's horizontal glue goes *before* the meta, never after it: navigator, `ActionListView` (whose rows became `BoxLayout.X_AXIS` for this; they carry no keycaps, so the meta and the source tag end the row) and `EditActionList`. Only the detail pane's **Action** fact row keeps it inline after the name — that is a label:value line with no keycap column to align to. Format (`actionMeta`): the action id in parentheses, the defining keymap in brackets, joined by a dash — `(id) - [Keymap]`, `(id)`, or `[Keymap]`. The defining keymap is the nearest ancestor that declares the id in its own scheme, else the base keymap that supplies a plugin/built-in default), and a trailing **Settings…** entry that opens the platform Keymap settings, carrying the same link arrow **after** its text — via the platform's `ActionUtil.SECONDARY_ICON` presentation property ("the icon that will be placed after the text", read by `ActionMenuItem.getSecondaryIcon()`; the route Git's "New" badge uses). `Presentation.setIcon` would put it in the left icon gutter instead, so the icon goes through the `menuAction(text, editableOnly, run, trailingIcon)` overload, which sets it on the **event's** presentation in `update()` so a template-presentation clone can't drop it), a prominent **summary**, and a **details** tree (the *navigator*) + **Swing** explanation pane (the *details*). Shortcuts render everywhere as **keycaps** — each modifier/key in its own rounded frame, matching Settings → Keymap — via the `Keycaps` util (`KeymapUtil.getKeystrokeText` split into per-cap glyphs; public-API only); the frame is always drawn in the glyph colour (the single "highlight" look — no dimmer variant). The navigator uses a **full-width `JPanel` tree renderer** laid out on a `BoxLayout.X_AXIS` so every part is **vertically centred**: `[icon + name] … glue … [dimmed id/keymap meta] [keycaps] [settings icon]` — the glue pushes the meta, keycaps and icon to the **right edge**: the cell is sized to **exactly** the viewport width (never wider, so the tree never scrolls horizontally and every row's keycaps end at the same x, with a ~12px right margin), re-aligning on resize via a row-height nudge. Name and meta are `shrinkable` (zero minimum → BoxLayout compresses them and Swing ellipsizes with "…"), the keycaps `rigid` (min = max = preferred), so an over-long row gives up text instead of pushing the keycaps out of alignment; such a row hands out the full `name + meta` as a **tooltip** (the tree is registered with `ToolTipManager` for it). The same shrinkable/rigid pairing right-aligns the keycaps in the dialogs' `EditActionList` rows. It paints its own selection background. The **rightmost column** is a per-row **settings icon** — `SETTINGS_ICON`, the `AllIcons.Ide.External_link_arrow` that `ActionLink.setExternalLinkIcon()` uses, tinted to `LINK_COLOR` (`JBUI.CurrentTheme.Link.Foreground.ENABLED`, also now the help "?" colour) so it reads as a link. It appears on every row that names an action (`rowActionId`: conflict/overlap/double-bound → the **first** action, Modified/Inherited → its own, Supplement → `actionId()`); section, subtitle and empty-placeholder rows get an equal-width strut instead so the keycap column stays aligned. A renderer can't receive clicks, so the **tree** carries a `MouseAdapter`: `settingsIconHit(e)` recomputes the icon's x-range from the row bounds (the cell always ends at the viewport edge, the icon is last, inside the `ROW_RIGHT_INSET` border — one constant shared by the border, the hit test and the tooltip) and a click there calls `openKeymapSettings(id)`; `mouseMoved` sets a hand cursor over it, and the renderer's `getToolTipText(MouseEvent)` returns "Open Keymap settings at …" for that x-range (falling back to the elision tooltip elsewhere). Each section shows a gray **subtitle info-row** as its first child when expanded (the `sectionSubtitle` one-liner; the full `sectionBlurb` stays in the details pane). **All five categories are always listed** — Keymap conflicts, Overlaps {ide} doesn't flag, Double-bound keys, Modified shortcuts, Inherited Shortcuts — so the set is stable and a category never disappears (previously "Overlaps" was omitted when empty and "Double-bound keys" had no placeholder at all); the **action filter** is the one exception (below). An empty one shows a single `Empty` placeholder row (`emptyRow`, ✔ `InspectionsOK` icon), and selecting it opens `buildEmptyDetail`: the category heading, the one-line status, the `emptyExplanation` of what would be listed there and why nothing is, and the `categoryLinks` row (just **Settings…** when the category is empty). The one placeholder that isn't good news — the JBR scan being unavailable — carries `ok=false`, a ⚠ `Warning` icon and its own text saying the section is empty because *nothing was scanned*. The gear's **Show modified only** still hides the other four; that filter is the whole point of the toggle. The **action filter** (`SearchTextField(false)` beside the combo — magnifier, ✕, no history popup; Esc clears it via the platform's `ClearText` action, which is disabled on an empty field so Esc still closes the dialog then; spec `spec/0004-action-search-filter.md`) is a pure **view filter over the current scan** — `applyFilter` → `rebuildTree()`, the same re-shape-don't-re-scan path as the toggles, keeping `filter` (trimmed + lowercased, for matching) and `filterText` (as typed, for the messages). It matches a case-insensitive **substring of the action's displayed name** (`ActionRef.label()`, which *is* the id when the platform names nothing) — **not** shortcut text and **not** ids; a row survives if **any** of its actions matches, not just the first one it displays. `buildRoot` is now five `addSection(root, title, rows(entries, payload), total, placeholder)` calls: `rows(…)` drops the non-matching payloads (`matchesFilter`), and `addSection` **omits the whole section** when the filter emptied it (its "nothing to fix ✔" placeholder would be a lie — the category may be full, just not of matches). `Section` carries `count` **and** `total`, rendered `(n)` or `(n of N)` so a filtered category can't read as a short one; `shouldExpand` opens **every** listed section while filtering (a collapsed match would defeat the filter); `categoryIds` filters too, so a category's bulk Remove…/Revert… can never reach past what the navigator shows. When **nothing** matches, the navigator is genuinely empty and carries the platform's `Tree.getEmptyText()` status (query + "the filter matches action names" + a clickable "Clear the filter"; `StatusText` centres lines without wrapping, so they stay short), while the detail pane shows the `NoMatch` payload — `buildNoMatchDetail`: what was searched, what wasn't (shortcuts, ids, plus the four categories "Show modified only" hides), that only actions **with** a shortcut are listed at all, then **Clear filter · Settings…**. It deliberately carries **no** amber ⚠ (unlike an empty *category*): nothing is wrong with the keymap, and the summary above still reports its real status. **Export…** ignores the filter by design — it writes the keymap, not the view. The report lists the selected keymap's conflicts as one set — its whole effective binding set (own declarations plus everything inherited from parents), all editable here — each action tagged with its providing plugin/IDE source where notable. From any conflict the detail pane shows a **Shortcut:** keycap header, the key and its status, then an **Actions** checkbox list (`ActionListView`): each action name is a link that highlights on hover (tooltip = the action's description) and, clicked, **rebinds that one action**; a **Select all**/**Deselect all** toggle drives the checkboxes. Below the list a dot-separated links row — **Rebind…** (moves the checked actions, or all if none are checked) · **Remove…** (clears the checked actions, or all if none checked, after a confirmation dialog) · **Revert…** (shown only when at least one action on the key is `revertable`; acts on the checked revertable ones, or all of them if the checkboxes name none) · **Settings…** (`settingsLink()` — opens the platform Keymap settings, with a trailing `External_link_arrow` icon signalling it leaves the plugin). Wherever a single action is in scope the link is `settingsLink(actionId)`, which **lands on that action**: `showSettingsDialog(project, KeymapPanel.class, panel -> panel.selectAction(actionId))` — the `Consumer` overload runs before the dialog shows and `selectAction` is documented to defer until the panel initializes, so it reveals + selects the action's tree node; the link also gets a tooltip naming it. Per-row details pass their own action, `linksRow` passes the key's **first** action (the one `actionsLabel`/`conflictMeta` already name, so the tooltip can't mislead), the unbound-supplement case passes its action (so a shortcut can be assigned there), and the category/empty rows keep the plain no-id link. There is **no** public way to preset the page's *find-by-shortcut* filter (`KeymapPanel.filterTreeByShortcut` and its filtering panel are private) and its text filter matches names/descriptions/**ids** but not shortcut text — so the action id is the only route in. Verified: `verifyPlugin` still reports **Compatible** with no API warnings. — sits above the "What to do" advice. Rebinding uses `ShortcutInputDialog`: the key field grabs a full keypress — even IDE-bound combos like ⌃X, because it intercepts via an `IdeEventQueue` dispatcher ahead of the keymap dispatcher — or a typed single key, or a radio for keys that can't be pressed into the field (↩ ⎋ ⌫ ⇥ **Space** — e.g. to build ⌘Esc; Space needs the radio because typed it is a blank that `trim()` discards and pressed bare it falls through to the field as plain typing, and its label is the *word* "Space" because that is what `MacKeymapUtil.getKeyText` renders for `VK_SPACE`, unlike the four glyph keys — so the radio matches the keycap), alongside modifier checkboxes and a live green/red status that flags a macOS overlap **and** an existing in-keymap binding of the new shortcut; keys map through `KeyEvent.getExtendedKeyCodeForChar`, so German keys Ä Ö Ü ß work, with manual correction when capture can't read a key. All three dialogs (Rebind/Remove/Revert) open with the affected-actions list **expanded** and **scrollable** (`cappedScroll`, ~480px tall so the window can't grow unbounded); a **Hide actions** checkbox on the button row (via `createDoNotAskCheckbox`) collapses it. Their centre panel is built by the shared `listLayout()`: the fixed form rows go `BorderLayout.NORTH`, the list's scroll pane `CENTER`. That split is load-bearing — NORTH always lays a component out at its **preferred** height and never shrinks it, so with the list inside the NORTH block (as it was) any window shorter than the whole form cut the bottom off *outside* the scroll pane, leaving those actions unreachable; Rebind hit it first because it stacks six more rows above the list. `CENTER` makes the list surrender the space and scroll instead. At the preferred size the layout is unchanged. The list is the shared `EditActionList` — one ticked checkbox row per action showing its name + id/keymap meta + **all** its current shortcuts as keycaps (and, for Revert, `→ reverts-to`), then the same trailing **settings icon** column as the navigator. In a dialog it can be a real `InplaceButton` (hover feedback + tooltip for free) rather than a painted icon plus hit test. Navigating away means abandoning the edit being confirmed — a half-ticked list can't be applied — so it **cancels the dialog** (`host.close(CANCEL_EXIT_CODE)`, the hosting `DialogWrapper` passed into the list's constructor) and then, on a later event so the modal loop unwinds first, calls `openKeymapSettings(id)`; the tooltip says "(closes this dialog)" outright. The rows' right inset is `ROW_RIGHT_INSET` too, so the icon sits the same distance from the edge as in the navigator. All three put a **Select all** / **Deselect all** link (`EditActionList.selectAllLink()`) *above* the scroll pane so it stays put while the list scrolls; it reads "Deselect all" while anything is ticked (matching `ActionListView`'s toggle, and how the dialogs open), follows the checkboxes, and is hidden together with the list by "Hide actions". Rebind and Remove omit it for a single-action list; Revert only builds a list in bulk mode anyway. Remove and Revert use Rebind's `FormBuilder` layout. **Remove**: keystroke-scoped when reached from a conflict (a **Current:** keycap header, clears that one key), else clears **all** shortcuts of each action (per-row/category `Remove…`, no single header); either way every affected action's full shortcut set is shown. **Revert**: single-action shows **Current:** / **Reverts to:** keycap rows; bulk shows the per-row `current → reverts-to` list, the "reverts-to" being the parent binding (`revertTarget`). The Rebind "New:" preview is live keycaps. All are `setResizable(true)` (movable on macOS). Any edit on a read-only keymap first derives, registers and activates an editable copy. The gear-menu **Export…** opens a dialog (`ExportDialog`) that writes either **all keys** (this keymap plus every parent down to `$default`, each level's `KeymapImpl.writeScheme` as one XML in a `.zip`) or any combination of four categories — **conflicts**, **overlaps**, **double-bound keys** (built from the effective bindings the scan reads, inherited ones included, serialized via `com.intellij.ui.KeyStrokeAdapter` so the exact platform format incl. umlaut hex is preserved), and **changes vs the parent** (the keymap's own declarations via `writeScheme`); one category exports as a bare `.xml`, several as a `.zip` with one XML per category. The gear-menu **Import…** is the reverse (`openImportDialog` → `parseImport` → `ImportDialog` → `performImport`): a single-`.xml` file chooser, then validation (root must be `<keymap>`; each `<action>`'s `keyboard-shortcut`/`mouse-shortcut`/`keyboard-gesture-shortcut` children are parsed with the platform's *own* public APIs — `KeyStrokeAdapter.getKeyStroke`, `KeymapUtil.parseMouseShortcut`, `KeyboardModifierGestureShortcut.newInstance` — so the format round-trips; unsupported elements are skipped with a note, malformed XML / wrong root / no actions are fatal). The dialog resolves the **name** (prefilled from the file, must be unique and non-reserved — live `doValidate`) and the **parent** (a combo of all installed keymaps). The file's `parent=` is resolved via `KeymapManager.getKeymap` (which sees internal roots like `$default` that `getAllKeymaps` hides — such a root is added to the combo so it stays pickable) and preselected when it exists; when it isn't installed, or none is declared, the combo opens on a `— Select a parent —` placeholder and `doValidate` puts a message in the **status line** ("… isn't installed — select a parent") that blocks OK until the user picks one. `performImport` then `deriveKeymap`s the chosen parent and replays every `<action>` (clear-then-add = the platform's replace semantics; an empty `<action/>` clears the inherited binding), `addScheme`s it and previews it **without activating** (like Duplicate). Imported keymaps are editable, so the gear menu's **Delete…** removes them fully. Conflict detection is runtime (JBR `com.jetbrains.SystemShortcuts` via reflection, same source as IDEA's own conflict banner; in-keymap duplicates via public `Keymap` API). Overlaps whose *only* macOS claim is window switching (ids `FocusNextApplicationWindow`/`FocusPreviousApplicationWindow`, which IntelliJ's own keymap tool hardcodes out of its banner — verified in `SystemShortcuts.readSystem` bytecode) are pulled into a separate, collapsed **"Overlaps IntelliJ doesn't flag"** section whose detail says so explicitly; they still work and stay fixable. That section is now always present (empty → placeholder), not conditional on having content. In-keymap duplicates (same keystroke on ≥2 actions) mirror IntelliJ's own `Keymap.getConflicts` — `$Editor` twins and use-shortcut-of aliases are filtered out — and are listed in the informational **"Double-bound keys"** section only, **not** flagged as conflicts: whether two actions truly clash depends on runtime context (focus, editor vs dialog, each action's enablement) that isn't statically knowable, so like IntelliJ's own tool we don't mark them — the Rebind dialog's live status warns at assignment time instead. A separate informational **"Modified shortcuts"** section (collapsed by default) lists the selected keymap's own declarations — its diff vs the parent (`KeymapImpl.writeScheme`, the same set the export's *changes* category reads, cleared inherited bindings included); each row shows the action and its current binding, and the detail offers the full edit links **Rebind… · Remove… · Revert… · Settings…** (`actionEditLinks`; Rebind moves the action's primary keystroke, Remove clears **all** its shortcuts). **Revert…** re-inherits the parent binding: for an **editable** keymap via `KeymapImpl.clearOwnActionsId` (drop the own declaration); for a **read-only** keymap, `revertToDefault` instead **replaces** the derived copy's binding with the read-only keymap's *own parent's* binding (clear-then-add) — because `deriveKeymap` of a read-only keymap yields a copy whose parent is that keymap with no own declarations, so `clearOwnActionsId` there would be a no-op (this fixes the earlier silent no-op). A `KeymapManagerListener.shortcutsChanged` publish then refreshes the live IDE. A parallel informational **"Inherited Shortcuts"** section (collapsed by default, hidden in "Show modified only") lists the effective bindings inherited from parent keymaps that this keymap doesn't declare — shortcut-bearing only (`ConflictScan.inherited`; actions with no shortcut are a Settings → Keymap job); its detail offers **Rebind… · Remove… · Settings…** — no Revert, but that now falls out of the `revertable` gate rather than a flag (an inherited binding has no own declaration to drop, so revert would be a no-op). Clicking a section **Title** (or its subtitle row) shows the blurb and the category-level links only (the earlier "contents listed in the pane" comfort view was reverted). Category links: **Inherited Shortcuts** gets only **Settings…**; every other category also gets bulk **Remove…** (clears all shortcuts of all its actions) and **Revert…** (its `revertable` ids only), both deselectable in the confirm dialog. **Revert…** is offered on **every** per-row detail — conflict, overlap, double-bound, supplement and Modified rows alike — gated on `revertable(id)` = "the viewed keymap declares this action itself" (`ownIds(keymap)`), because only an own declaration can be dropped for the parent binding to re-inherit; anything else already equals the parent, so the link would be inert and is hidden. `confirmRevert` no-ops on an empty list. The gear's **Show modified only** toggle filters the report to just the Modified section (implements YouTrack IJPL-228176 in the plugin's own dialog; see `spec/0001-modified-shortcuts-filter.md`). There is no longer an ours/outside ownership split: the selected keymap's whole effective set is treated as its own (all editable, so an "outside" bucket would be pointless). The curated `SUPPLEMENT` extras are shown by `activeSupplements()` for **any** keymap that actually **binds** the supplement's action (`keymap.getShortcuts(actionId).length > 0`) — no longer gated on an `ownKeymap` flag (that flag, and `ConflictScan.isOurKeymap`, were removed; it's why the "Overlaps…" section previously appeared only for the bundled keymap). Each `Supplement` names the IDE action it concerns (`actionId` — `EmojiAndSymbols`, `RunAnything`), so its detail (`buildSupplementDetail`) offers the same **Rebind…/Remove…/Revert…/Settings…** on that action (Rebind only when it's a keystroke — `RunAnything` is a double-⌃ gesture, so it gets Remove/Settings; Revert only when the action is `revertable`); the macOS side is still changed in System Settings. Curated per-conflict advice lives in `ConflictAdvice` (keep in sync with `keys.md` Appendix C). User-facing strings use a `{ide}` placeholder for the host IDE's name (never hardcode "IntelliJ"/"IDEA" in shown text — the plugin runs on any IntelliJ-Platform IDE); it is substituted once at render by `ConflictReportDialog.subIde()` — via `htmlPane()` and the tree renderer, plus an `IDE_NAME` splice for the one plain-label status — to `ApplicationNamesInfo.getFullProductName()`, so the report reads "PyCharm" / "Android Studio" / … off IntelliJ IDEA. Keep the surface focused — the plugin is a **macOS-focused keymap manager**: conflict resolution plus the rebind/export/import and keymap-management tools that serve it, with the bundled keymap as a ready-made starting point. The boundary (see `spec/0002-plugin-scope-and-name.md` and `spec/0003-full-keymap-editing-and-keycaps.md`, which superseded 0002's editing rudder): stay macOS-focused (the live system-shortcut scan is the differentiator), and edit **every bound shortcut** (own or inherited) in place — but still **not every *action***: binding a shortcut onto an action that has none stays a Settings → Keymap job (every category detail links to it).

## Keymap XML invariants

- Filename and the `name=` attribute must match exactly (`MacBook Pro DE` / `MacBook Pro DE.xml`). **Never rename the keymap** — users who selected it would be silently reverted to the default.
- `parent="Mac OS X 10.5+"`. The name must not start with `Mac OS X` (triggers `MacOSDefaultKeymap` modifier conversion) and must not reuse an official keymap name (`Eclipse`, `Emacs`, `NetBeans 6.5`, `QtCreator`, `ReSharper`, `Sublime Text`, `Visual Studio`, `Visual Assist`, `Xcode`, `Rider`, `VSCode`, `macOS System Shortcuts`, or their `… OSX`/`… (Mac OS X)` variants — canonical list in `notifyAboutMissingKeymap`, `KeymapImpl.kt`).
- Empty `<action id="X"/>` elements are **load-bearing** — they clear bindings inherited from the parent. Do not remove them as cleanup.
- German-layout rule: bindings address *physical keys* (VK codes), not characters. Never bind `SLASH`, `BACK_SLASH`, `OPEN_BRACKET`, `CLOSE_BRACKET`, `SEMICOLON`, `QUOTE`, `BACK_QUOTE`, `EQUALS` (no physical key on German T1), `INSERT` (no Mac key), or numpad keys `ADD`/`SUBTRACT`/`MULTIPLY`/`DIVIDE`/`NUMPADn` (MacBook Pro has no numpad).
- `Ä Ö Ü ß` are bindable via extended hex codes (`meta #10000d6` = ⌘Ö). Do not compute the codes by hand — `Ü` breaks the codepoint pattern. The machine-verified values are tabulated in `keymaps/keys.md` ("Bindable German keys").

## Gradle gotchas (already hit once)

- The platform dependency must use the Maven repository, not installers: `intellijIdeaCommunity("2026.1.4") { useInstaller = false }` — installer URL resolution fails for this version. Note `useInstaller` is set inside the configuration lambda; the named-parameter form no longer exists in IntelliJ Platform Gradle Plugin 2.18+.
- `buildSearchableOptions = false` stays off — the task boots a headless IDE for nothing in a resource-only plugin.
- `sinceBuild = "261"` with **no** `untilBuild` is deliberate: the plugin has no API surface, so capping compatibility only forces pointless re-releases.
- The build prints "IntelliJ IDEA Community (IC) is no longer published since 2025.3, use: intellijIdea(...)". The pinned `intellijIdeaCommunity("2026.1.4")` still resolves; switch to `intellijIdea("...")` when next bumping the platform version.
- `verifyPlugin` (IntelliJ Plugin Verifier) needs its target IDE pinned explicitly: `recommended()` resolves **empty** for build 261 (2026.1 is too new for the bundled recommended list). The `pluginVerification { ides { … } }` block uses `create(IntelliJPlatformType.IntellijIdeaCommunity, "2026.1.4") { useInstaller = false }` — the `create(...)` overload (there is **no** `ide(...)` method on that receiver), with `useInstaller = false` for the same Maven-resolution reason as the compile dependency; needs the top-level `import org.jetbrains.intellij.platform.gradle.IntelliJPlatformType`. Last run: verdict **Compatible**, zero API warnings.
- The plugin is a fully **dynamic plugin**: a fresh install, enable/disable, and a Marketplace update all apply without an IDE restart. Confirmed three ways — the Plugin DevKit inspection *Plugin.xml dynamic plugin verification* (Analyze → Run Inspection by Name…) reports zero findings; `verifyPlugin` prints "Dynamic Plugin Eligibility: Plugin can probably be enabled or disabled without IDE restart"; and a live install of the built ZIP (Settings → Plugins → gear → Install Plugin from Disk) activated immediately, bundled keymap included, no restart banner — the real IDE's `idea.log` shows the matching `DynamicPlugins - … load plugin 'Keymap Manager'` / `unload plugin …` pairs. **But "Install Plugin from Disk" over an already-installed copy always asks for a restart, and that says nothing about the plugin.** `PluginInstaller.installFromDisk` computes `isRestartRequired = oldFile != null || !allowLoadUnloadWithoutRestart(…) || …`, so an existing non-bundled installation **short-circuits** the dynamic check (which is why no `DynamicPlugins` line appears in the log at all, and why bumping the version doesn't help); the install is staged as a Delete+Unzip in `$caches/plugins/action.script` for the next start. To iterate dynamically, **uninstall first, then install** the new ZIP (or just use `runIde`). Two session-global gates also force a restart on *any* path: `InstalledPluginsState.isRestartRequired` ("… because of pending restart operation" — sticky once anything in the session scheduled a restart) and a leftover classloader from an incomplete earlier unload. The Marketplace path is different code (`PluginInstallOperation` with `allowInstallWithoutRestart` → `installAndLoadDynamicPlugin`, unloading the running version first via `uninstallDynamicPlugin(…, isUpdate=true)`), so a Marketplace update loads live unless that unload fails ("Plugin … is still loaded, restart is required"). Every extension point in `plugin.xml` — `bundledKeymap`, `notificationGroup`, `<actions>`, `applicationListeners` — is dynamic-capable in the platform. Don't trust web searches on individual extension points' `dynamic=` attribute (tried and got a wrong answer, since retracted); re-run the inspection or do a live-install test instead.
