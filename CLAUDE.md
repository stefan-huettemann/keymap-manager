# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A **JetBrains plugins project** (see `README.md`). The active plugin is **Keymap Manager** (ID `de.civa.plugins.keymapmanager`, display name "Keymap Manager"). It is a **macOS-focused keymap manager**: find and resolve shortcut conflicts, rebind/remove shortcuts in place, import/export keymaps as XML, and manage installed keymaps (select/activate/duplicate/rename/delete); it also bundles the **MacBook Pro DE** keymap as a ready-made starting point for JetBrains IDEs on macOS. The driving constraint for that keymap is a **German (T1/ISO) keyboard on a MacBook Pro** — many stock IntelliJ bindings are physically unpressable there and are being replaced.

`keymaps/keys.md` is the canonical reference: the German-layout constraint, the audit of every key the keymap uses, and the machine-verified table of bindable German keys (umlaut hex encoding). Read it before touching keymap XML. (A more detailed research doc, `handover-unreachable-keys.md`, exists locally but is gitignored — do not rely on it being present.)

## Commands

```bash
# Build the plugin ZIP  →  keymap-plugin/build/distributions/Keymap-Manager-<version>.zip
# (<version> comes from build.gradle.kts; currently 1.6.0)
cd keymap-plugin && ./gradlew buildPlugin

# Launch a sandbox IDE with the plugin loaded (for manual verification)
cd keymap-plugin && ./gradlew runIde

# Verify API compatibility against the target IDE (internal/experimental/deprecated-API usage)
# → verdict under build/reports/pluginVerifier/<IDE>/…/verification-verdict.txt
cd keymap-plugin && ./gradlew verifyPlugin
```

There are no tests or linters. After editing keymap XML, verify with an ad-hoc Python script (xml.etree): well-formed, action ids unique and alphabetically sorted, every id present in `keymaps/$default.xml` or `keymaps/Mac OS X 10.5+.xml` (unknown ids fail **silently** at runtime), and only `keyboard-shortcut` / `mouse-shortcut` / `keyboard-gesture-shortcut` child elements (anything else throws `InvalidDataException` at load). Exception to the id check: three intentional empty `<action/>` overrides — `Terminal.ClearPrompt`, `Terminal.SearchInCommandHistory`, `Vcs.CombinedDiff.ToggleCollapseBlock` — are **not** in the reference keymaps; they clear conflicting plugin default shortcuts (Terminal/VCS ship in all JetBrains IDEs), so don't treat them as unknown-id errors.

Install/activation steps for the built ZIP: `keymap-plugin/INSTALL.md`.

## Structure and data flow

- `keymaps/MacBook Pro DE.xml` — **working copy / source of truth** for the keymap. It is a *flattened* merge of `$default.xml` and `Mac OS X 10.5+.xml` (Mac entries win; stale conflicting shortcuts pruned): all ~447 bindings are re-stated explicitly even though `parent="Mac OS X 10.5+"` would inherit most, deliberately pinning them against upstream changes.
- `keymap-plugin/src/main/resources/keymaps/MacBook Pro DE.xml` — the plugin resource, a **manual copy** of the file above. After editing the working copy, `cp` it here and rebuild; nothing syncs them automatically.
- `keymaps/$default.xml`, `keymaps/Mac OS X 10.5+.xml` — reference copies of the platform keymaps. All three keymap files are sorted alphabetically by action id for side-by-side diffing; keep them sorted.
- `keymaps/orig/` — pristine platform exports; do not modify.
- `keymaps/keys.md` — generated audit of every modifier/key used, with German-layout reachability. Appendix A (37 actions with no reachable binding) is the rebinding work list.
- `keymap-plugin/` — Gradle project: `plugin.xml` + the keymap XML, wired via the `bundledKeymap` extension point, plus six Java classes: `NationalLayoutCheck` fires a startup/keymap-change notification for **whatever keymap is active** — a warning with a one-click fix when *our* keymap is active while JBR national keyboard layout support (`com.sun.awt.use.national.layouts`, default on for macOS) is off (without which the German-key bindings never fire), otherwise a plain nudge to review conflicts; the warning and the nudge latch **independently** (one-shot each), so switching to our keymap still warns even if the nudge already fired; both carry the "Open Keymap Manager" action. `ConflictScan` + `ConflictAdvice` + `ConflictReportDialog` implement the live report, also opened by `ShowConflictReportAction` (Tools → Keymap Manager). The dialog has three parts — a keymap **selector** (dropdown of all installed keymaps: active first, then this plugin's, then the rest, each tagged with its source; Activate/Reset for a non-active pick, plus a **gear menu** — a flat `InplaceButton` whose icon is a `LayeredIcon` of `GearPlain` with `ButtonDropTriangle` overlaid at the bottom-right corner, opening a real IDEA action menu (`ActionManager.createActionPopupMenu`) — holding **Export…**, **Import…** and **Duplicate** (derive an editable copy and preview it) always, **Rename**/**Delete** for an editable keymap (Rename inline in the combo's slot via a CardLayout swap — Esc cancels, Enter saves, re-registered under the new name (duplicate names, and reserved ones — the `Mac OS X` prefix or an official keymap name — are refused); Delete with confirmation, falling back to the parent keymap), and, in a separate bottom section, a **Show modified only** toggle (hides the conflict sections, leaving just the Modified-shortcuts view) and a **Show Action IDs** toggle and a **Show Keymap** toggle (both default off — Show Action IDs appends each action's id, Show Keymap appends the keymap that *defines* the current binding (nearest declaring ancestor up the parent chain, `definingKeymapName`); shown **dimmed** next to the action name in **every** surface — navigator (incl. conflict/double-bound/overlap rows, via the first action), detail pane, the conflict action list (`ActionListView`), the section-contents listing, and the confirm-dialog lists. Format (`actionMeta`): the defining keymap first in parentheses, the id in brackets after it — `(Keymap [id])`, `(Keymap)`, or `[id]`. The defining keymap is the nearest ancestor that declares the id in its own scheme, else the base keymap that supplies a plugin/built-in default), and a trailing **Settings…** entry that opens the platform Keymap settings), a prominent **summary**, and a **details** tree (the *navigator*) + **Swing** explanation pane (the *details*). Shortcuts render everywhere as **keycaps** — each modifier/key in its own rounded frame, matching Settings → Keymap — via the `Keycaps` util (`KeymapUtil.getKeystrokeText` split into per-cap glyphs; public-API only); the frame is always drawn in the glyph colour (the single "highlight" look — no dimmer variant). The navigator uses a **full-width `JPanel` tree renderer** laid out on a `BoxLayout.X_AXIS` so every part is **vertically centred**: `[icon + name] … glue … [dimmed id/keymap meta] [keycaps]` — the glue pushes the meta + keycaps to the **right edge** (the cell stretches to the viewport, re-aligning on resize via a row-height nudge); it paints its own selection background. Each section shows a gray **subtitle info-row** as its first child when expanded (the `sectionSubtitle` one-liner; the full `sectionBlurb` stays in the details pane). The report lists the selected keymap's conflicts as one set — its whole effective binding set (own declarations plus everything inherited from parents), all editable here — each action tagged with its providing plugin/IDE source where notable. From any conflict the detail pane shows a **Shortcut:** keycap header, the key and its status, then an **Actions** checkbox list (`ActionListView`): each action name is a link that highlights on hover (tooltip = the action's description) and, clicked, **rebinds that one action**; a **Select all**/**Deselect all** toggle drives the checkboxes. Below the list a dot-separated links row — **Rebind…** (moves the checked actions, or all if none are checked) · **Remove…** (clears the checked actions, or all if none checked, after a confirmation dialog) · **Settings…** (`settingsLink()` — opens the platform Keymap settings, with a trailing `External_link_arrow` icon signalling it leaves the plugin) — sits above the "What to do" advice. Rebinding uses `ShortcutInputDialog`: the key field grabs a full keypress — even IDE-bound combos like ⌃X, because it intercepts via an `IdeEventQueue` dispatcher ahead of the keymap dispatcher — or a typed single key, or a radio for keys that can't be pressed into the field (↩ ⎋ ⌫ ⇥ — e.g. to build ⌘Esc), alongside modifier checkboxes and a live green/red status that flags a macOS overlap **and** an existing in-keymap binding of the new shortcut; keys map through `KeyEvent.getExtendedKeyCodeForChar`, so German keys Ä Ö Ü ß work, with manual correction when capture can't read a key. All three dialogs (Rebind/Remove/Revert) open with the affected-actions list **expanded** and **scrollable** (`cappedScroll`, ~480px tall so the window can't grow unbounded); a **Hide actions** checkbox on the button row (via `createDoNotAskCheckbox`) collapses it. The list is the shared `EditActionList` — one ticked checkbox row per action showing its name + id/keymap meta + **all** its current shortcuts as keycaps (and, for Revert, `→ reverts-to`). Remove and Revert use Rebind's `FormBuilder` layout. **Remove**: keystroke-scoped when reached from a conflict (a **Current:** keycap header, clears that one key), else clears **all** shortcuts of each action (per-row/category `Remove…`, no single header); either way every affected action's full shortcut set is shown. **Revert**: single-action shows **Current:** / **Reverts to:** keycap rows; bulk shows the per-row `current → reverts-to` list, the "reverts-to" being the parent binding (`revertTarget`). The Rebind "New:" preview is live keycaps. All are `setResizable(true)` (movable on macOS). Any edit on a read-only keymap first derives, registers and activates an editable copy. The gear-menu **Export…** opens a dialog (`ExportDialog`) that writes either **all keys** (this keymap plus every parent down to `$default`, each level's `KeymapImpl.writeScheme` as one XML in a `.zip`) or any combination of four categories — **conflicts**, **overlaps**, **double-bound keys** (built from the effective bindings the scan reads, inherited ones included, serialized via `com.intellij.ui.KeyStrokeAdapter` so the exact platform format incl. umlaut hex is preserved), and **changes vs the parent** (the keymap's own declarations via `writeScheme`); one category exports as a bare `.xml`, several as a `.zip` with one XML per category. The gear-menu **Import…** is the reverse (`openImportDialog` → `parseImport` → `ImportDialog` → `performImport`): a single-`.xml` file chooser, then validation (root must be `<keymap>`; each `<action>`'s `keyboard-shortcut`/`mouse-shortcut`/`keyboard-gesture-shortcut` children are parsed with the platform's *own* public APIs — `KeyStrokeAdapter.getKeyStroke`, `KeymapUtil.parseMouseShortcut`, `KeyboardModifierGestureShortcut.newInstance` — so the format round-trips; unsupported elements are skipped with a note, malformed XML / wrong root / no actions are fatal). The dialog resolves the **name** (prefilled from the file, must be unique and non-reserved — live `doValidate`) and the **parent** (a combo of all installed keymaps). The file's `parent=` is resolved via `KeymapManager.getKeymap` (which sees internal roots like `$default` that `getAllKeymaps` hides — such a root is added to the combo so it stays pickable) and preselected when it exists; when it isn't installed, or none is declared, the combo opens on a `— Select a parent —` placeholder and `doValidate` puts a message in the **status line** ("… isn't installed — select a parent") that blocks OK until the user picks one. `performImport` then `deriveKeymap`s the chosen parent and replays every `<action>` (clear-then-add = the platform's replace semantics; an empty `<action/>` clears the inherited binding), `addScheme`s it and previews it **without activating** (like Duplicate). Imported keymaps are editable, so the gear menu's **Delete…** removes them fully. Conflict detection is runtime (JBR `com.jetbrains.SystemShortcuts` via reflection, same source as IDEA's own conflict banner; in-keymap duplicates via public `Keymap` API). Overlaps whose *only* macOS claim is window switching (ids `FocusNextApplicationWindow`/`FocusPreviousApplicationWindow`, which IntelliJ's own keymap tool hardcodes out of its banner — verified in `SystemShortcuts.readSystem` bytecode) are pulled into a separate, collapsed **"Overlaps IntelliJ doesn't flag"** section whose detail says so explicitly; they still work and stay fixable. In-keymap duplicates (same keystroke on ≥2 actions) mirror IntelliJ's own `Keymap.getConflicts` — `$Editor` twins and use-shortcut-of aliases are filtered out — and are listed in the informational **"Double-bound keys"** section only, **not** flagged as conflicts: whether two actions truly clash depends on runtime context (focus, editor vs dialog, each action's enablement) that isn't statically knowable, so like IntelliJ's own tool we don't mark them — the Rebind dialog's live status warns at assignment time instead. A separate informational **"Modified shortcuts"** section (collapsed by default) lists the selected keymap's own declarations — its diff vs the parent (`KeymapImpl.writeScheme`, the same set the export's *changes* category reads, cleared inherited bindings included); each row shows the action and its current binding, and the detail offers the full edit links **Rebind… · Remove… · Revert… · Settings…** (`actionEditLinks`; Rebind moves the action's primary keystroke, Remove clears **all** its shortcuts). **Revert…** re-inherits the parent binding: for an **editable** keymap via `KeymapImpl.clearOwnActionsId` (drop the own declaration); for a **read-only** keymap, `revertToDefault` instead **replaces** the derived copy's binding with the read-only keymap's *own parent's* binding (clear-then-add) — because `deriveKeymap` of a read-only keymap yields a copy whose parent is that keymap with no own declarations, so `clearOwnActionsId` there would be a no-op (this fixes the earlier silent no-op). A `KeymapManagerListener.shortcutsChanged` publish then refreshes the live IDE. A parallel informational **"Inherited Shortcuts"** section (collapsed by default, hidden in "Show modified only") lists the effective bindings inherited from parent keymaps that this keymap doesn't declare — shortcut-bearing only (`ConflictScan.inherited`; actions with no shortcut are a Settings → Keymap job); its detail offers **Rebind… · Remove… · Settings…** (no Revert — an inherited binding already equals the parent). Clicking a section **Title** (or its subtitle row) shows the blurb, the category-level links, and the category's **contents listed in the pane** (`sectionListing` — each row's name selects that item in the navigator; comfort, so you needn't expand the tree). Category links: **Inherited Shortcuts** gets only **Settings…**; every other category also gets bulk **Remove…** (clears all shortcuts of all its actions) and **Revert…**, both deselectable in the confirm dialog. The gear's **Show modified only** toggle filters the report to just the Modified section (implements YouTrack IJPL-228176 in the plugin's own dialog; see `spec/0001-modified-shortcuts-filter.md`). There is no longer an ours/outside ownership split: the selected keymap's whole effective set is treated as its own (all editable, so an "outside" bucket would be pointless). The curated `SUPPLEMENT` extras are shown by `activeSupplements()` for **any** keymap that actually **binds** the supplement's action (`keymap.getShortcuts(actionId).length > 0`) — no longer gated on an `ownKeymap` flag (that flag, and `ConflictScan.isOurKeymap`, were removed; it's why the "Overlaps…" section previously appeared only for the bundled keymap). Each `Supplement` names the IDE action it concerns (`actionId` — `EmojiAndSymbols`, `RunAnything`), so its detail (`buildSupplementDetail`) offers the same **Rebind…/Remove…/Settings…** on that action (Rebind only when it's a keystroke — `RunAnything` is a double-⌃ gesture, so it gets Remove/Settings); the macOS side is still changed in System Settings. Curated per-conflict advice lives in `ConflictAdvice` (keep in sync with `keys.md` Appendix C). User-facing strings use a `{ide}` placeholder for the host IDE's name (never hardcode "IntelliJ"/"IDEA" in shown text — the plugin runs on any IntelliJ-Platform IDE); it is substituted once at render by `ConflictReportDialog.subIde()` — via `htmlPane()` and the tree renderer, plus an `IDE_NAME` splice for the one plain-label status — to `ApplicationNamesInfo.getFullProductName()`, so the report reads "PyCharm" / "Android Studio" / … off IntelliJ IDEA. Keep the surface focused — the plugin is a **macOS-focused keymap manager**: conflict resolution plus the rebind/export/import and keymap-management tools that serve it, with the bundled keymap as a ready-made starting point. The boundary (see `spec/0002-plugin-scope-and-name.md` and `spec/0003-full-keymap-editing-and-keycaps.md`, which superseded 0002's editing rudder): stay macOS-focused (the live system-shortcut scan is the differentiator), and edit **every bound shortcut** (own or inherited) in place — but still **not every *action***: binding a shortcut onto an action that has none stays a Settings → Keymap job (every category detail links to it).

## Keymap XML invariants

- Filename and the `name=` attribute must match exactly (`MacBook Pro DE` / `MacBook Pro DE.xml`). **Never rename the keymap** — users who selected it would be silently reverted to the default.
- `parent="Mac OS X 10.5+"`. The name must not start with `Mac OS X` (triggers `MacOSDefaultKeymap` modifier conversion) and must not reuse an official keymap name (`Eclipse`, `Emacs`, `NetBeans 6.5`, `QtCreator`, `ReSharper`, `Sublime Text`, `Visual Studio`, `Visual Assist`, `Xcode`, `Rider`, `VSCode`, `macOS System Shortcuts`, or their `… OSX`/`… (Mac OS X)` variants — canonical list in `notifyAboutMissingKeymap`, `KeymapImpl.kt`).
- Empty `<action id="X"/>` elements are **load-bearing** — they clear bindings inherited from the parent. Do not remove them as cleanup.
- German-layout rule: bindings address *physical keys* (VK codes), not characters. Never bind `SLASH`, `BACK_SLASH`, `OPEN_BRACKET`, `CLOSE_BRACKET`, `SEMICOLON`, `QUOTE`, `BACK_QUOTE`, `EQUALS` (no physical key on German T1), `INSERT` (no Mac key), or numpad keys `ADD`/`SUBTRACT`/`MULTIPLY`/`DIVIDE`/`NUMPADn` (MacBook Pro has no numpad).
- `Ä Ö Ü ß` are bindable via extended hex codes (`meta #10000d6` = ⌘Ö). Do not compute the codes by hand — `Ü` breaks the codepoint pattern. The machine-verified values are tabulated in `keymaps/keys.md` ("Bindable German keys").

## Gradle gotchas (already hit once)

- The platform dependency must use the Maven repository, not installers: `intellijIdeaCommunity("2026.1.4") { useInstaller = false }` — installer URL resolution fails for this version. Note `useInstaller` is set inside the configuration lambda; the named-parameter form no longer exists in IntelliJ Platform Gradle Plugin 2.18+.
- `buildSearchableOptions = false` stays off — the task boots a headless IDE for nothing in a resource-only plugin.
- `sinceBuild = "261"` with **no** `untilBuild` is deliberate: the plugin has no API surface, so capping compatibility only forces pointless re-releases.
- The build prints "IntelliJ IDEA Community (IC) is no longer published since 2025.3, use: intellijIdea(...)". The pinned `intellijIdeaCommunity("2026.1.4")` still resolves; switch to `intellijIdea("...")` when next bumping the platform version.
- `verifyPlugin` (IntelliJ Plugin Verifier) needs its target IDE pinned explicitly: `recommended()` resolves **empty** for build 261 (2026.1 is too new for the bundled recommended list). The `pluginVerification { ides { … } }` block uses `create(IntelliJPlatformType.IntellijIdeaCommunity, "2026.1.4") { useInstaller = false }` — the `create(...)` overload (there is **no** `ide(...)` method on that receiver), with `useInstaller = false` for the same Maven-resolution reason as the compile dependency; needs the top-level `import org.jetbrains.intellij.platform.gradle.IntelliJPlatformType`. Last run: verdict **Compatible**, zero API warnings.
